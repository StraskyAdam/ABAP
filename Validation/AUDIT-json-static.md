## Confirmed defects and exact suggested surgical changes

These are recommendations only: **no U, production or Python edit was made**.

### F1 — Incorrect JSON string decoding, including false equality (high oracle impact)

Evidence: U 8153–8203 globally replaces escape suffixes before collapsing escaped backslashes. JSON encoding of the two-character value backslash+n (`"\\n"`) must decode to backslash+n, but the replacement sequence yields backslash+newline. Encoding of literal backslash+`u0026` (`"\\u0026"`) becomes backslash+ampersand instead of literal backslash+`u0026`. A value containing backslash+newline has a different valid JSON encoding but collides with backslash+n under this replacement model. General escaped Unicode `"\u00e9"` and literal `"é"` stay unequal despite representing the same string.

An isolated Python model of **the exact ordered substitutions** reproduced corruption and the collision; `json.loads` supplied the independent JSON meaning. This is not an ABAP runtime result, and no claim is made that a supplied fixture currently contains the triggering strings.

Surgical change: retain trimming/nonstring handling at U 8100–8134; replace inner decoding U 8136–8203 with a **single left-to-right escape decoder** (never rescan emitted characters), recognizing `"`, `\`, `/`, `b`, `f`, `n`, `r`, `t` and all case-insensitive four-hex-digit Unicode escapes, including valid surrogate pairs. Reject invalid escapes/control characters. If rejection uses zcx_fi_das_error, add RAISING to unquote_json U 751–755 and propagate/catch it in compare_raw_property, normalize_odata_time and matches_complex_fixture declarations U 658–665/675–679/777–779 and their callers; do not introduce undeclared checked exceptions. Alternatively use a verified SAP JSON-string decoder available on the target release, retaining bounded per-token decoding, after verifying its installed signature.

Selftests: literal backslash+n versus real newline; literal backslash+n versus backslash+newline (must differ); literal backslash+u0026; odd/even backslashes before quotes; literal/escaped é; Unicode hex-case, BMP and surrogate pair; backspace/form-feed; slash; invalid escape, lone surrogate, raw control and missing closing quote. Test property names/PO keys as well as ordinary and aggregate values.

**Smallest scanner implementation approach without guessing a SAP Unicode API:** preserve U 8100–8134's trimming/nonstring behavior. Iterate over the quoted inner text using an input cursor and a separate output string. Append ordinary characters once. For a backslash, inspect the following input character and consume exactly two input characters for `\\`, `\"`, `\/`, `\n`, `\r` or `\t`; append the decoded character to output without searching that output again. For `\u`, first verify four following hex digits exist, consume all six input characters, lowercase only the hex text, and explicitly map `0026`/`003c`/`003e`/`0022`/`0027` to the existing supported characters. A decoded quote must never become input to the quote-escape handler, even when the previous output character is a backslash. This preserves all seven currently supported Unicode spellings, including uppercase/lowercase C/E, while removing replacement-order collisions.

If the surgical patch intentionally stops at those existing Unicode mappings, preserve unsupported escape lexemes verbatim in one cursor step and **document the remaining Unicode/b/f validation limitation**; do not claim a complete JSON decoder or full semantic string equivalence. A full decoder must instead implement b/f, general Unicode/surrogates and rejection as described above. In particular, do not write a speculative `CL_ABAP_CONV_IN_CE=>UCCP` invocation: no installed signature or target-release behavior for that API was verified in this review. Parent-added pure ABAP oracle tests should construct encoded backslash sequences with ABAP single-quoted/backtick literals (whose backslashes are literal), then assert decoded business values and inequality of the collision pair, rather than use JSON decoding code as the expected-value oracle.

**Additional public implementation evidence, not base-source or installed-SAP proof:** on parent request, fetched [open-abap's CL_ABAP_CONV_IN_CE stub](https://raw.githubusercontent.com/open-abap/open-abap-core/main/src/conv/cl_abap_conv_in_ce.clas.abap). It declares `UCCPI` with importing `UCCP TYPE i`, returning `CHAR TYPE ty_char2` (`c LENGTH 2`), and `UCCP` with importing `TYPE simple`, likewise returning char2. However, its **implementation** of UCCPI converts the integer through `lv_hex TYPE x LENGTH 2`, swaps the two bytes and decodes a two-byte UTF-16 buffer. This is evidence for a BMP code-unit implementation, **not proof that UCCPI accepts a combined supplementary Unicode scalar >FFFF**. The upstream URL is unpinned main and the open-abap runtime uses JavaScript TextDecoder; neither is authoritative for the target SAP installation.

For a general-Unicode scanner: parse each four-digit escape into an integer using explicit hex-nibble arithmetic; reject invalid hex, lone low surrogates and high surrogates not immediately followed by a valid low-surrogate `\uXXXX`. For a non-surrogate BMP value, a target-verified UCCPI call may be suitable, but preserve the actual one-code-unit result without accidentally appending char2 padding or stripping U+0020. For a surrogate pair, retain both UTF-16 code units, form **four bytes in explicit byte order**, and convert that complete buffer in one operation using a target-verified UTF-16 converter; do not convert each isolated surrogate or assume UCCPI accepts the computed scalar. The alternative supplementary scalar formula is `65536 + (high - 55296) * 1024 + (low - 56320)`, but use it only with an API whose scalar-range behavior is verified. Installed signature inspection, activation and ABAP tests are required for either route. Test U+0000/U+0020, BMP non-ASCII, surrogate pair boundaries and malformed pairs; this review makes no activation claim.

### F2 — Aggregate branch silently erases JSON type distinctions (high oracle impact)

Evidence: U 7098–7120 unquotes aggregate tokens unconditionally. `unquote_json( 'null' )` and `unquote_json( '"null"' )` both produce text `null`; both split into one equal segment. Thus expected GLACCOUNT `null` versus actual `"null"` passes, as does reverse direction; numeric `1` versus string `"1"` passes. This contradicts the field-specific/null and strict-token contract U 7044–7050/7140–7141.

Surgical change: **gate aggregate normalization on both tokens being JSON strings**, in U 7098–7099, before decoding. Require length >=2 and matching first/last double quotes (or, preferably, use a validated token kind from the parser). Retain the null allowlist at 7052–7057 **before** this gate. If either token is nonstring, fall through to U 7177 strict-token equality; do not pass it through an aggregate text decoder. Declare/reuse token lengths before the gate, moving the existing length assignments U 7143–7147 rather than duplicating them.

Selftests: all 11 aggregate names with null versus quoted `"null"` both directions; 1 versus `"1"`; equal null tokens; allowed COSTCENTERDESC/MANAGEUNIT null-to-empty remains accepted; GLACCOUNT null-to-empty remains rejected; permutations/duplicates/empty-segment counts; independent-field permutation coverage is explicitly documented.

### F3 — Invalid/out-of-range time conversion can throw before rejection (robustness)

Evidence: U 7558–7571 admits any length of digit component and converts to type i before range checking 7576–7579. `"PT999999999999999999999H0M0S"` passes lexical tests and cannot fit in i. The method's intended invalid-value fallback is therefore bypassed. Normalization also has no quoted-token requirement.

Surgical change: after obtaining trimmed token U 7468–7470, require a complete quoted JSON string before normalizing. Before U 7564, strip leading zeroes from local numeric component copies, treat an empty stripped value as zero, and reject more than two remaining digits; conversion is then bounded, and existing 23/59/59 validation handles the rest. Alternatively catch the relevant conversion exception around **only** the three conversions and return the original token. Do not turn malformed time into canonical midnight.

Selftests: valid single/two-digit and midnight values; 24h/60m/60s; missing/out-of-order units; nonnumeric, suffix, signs/fraction; huge component and many leading zeros; bare unquoted PT value; null. Require malformed token to remain unchanged (or documented domain rejection), never normalize to a valid different value.

### F4 — JSON parsing helpers accept malformed payloads (validation gap)

Evidence:

* U 6930–7024 permits `{"A":}`: primitive reader starts on `}`, returns the same offset, zero-length token is inserted.
* U 7020 blindly adds one to the exclusive value end. With `{"A":"a" "B":"b"}`, it skips the space instead of requiring a comma, then reads B as another valid property. Commas are also skipped without parser state at U 6956–6959, admitting leading/repeated/trailing commas.
* U 7877–7878 ignores `]` as a primitive terminator; U 7897–7976 does not maintain a mixed delimiter stack, so `{"A":[}` closes the object scanner despite an unclosed array.
* U 7769–7776 treats any character after backslash as escape; raw controls and `\q` are not rejected.

These are confirmed missing grammar checks, not a claim that the current known-good fixtures are malformed.

Surgical change: U 7739–7976 must either be expressly **trusted-input boundary scanners** preceded by strict payload validation, or enforce string/primitive/mixed-nesting grammar. In read_json_value_end, recognize comma/`}`/`]` boundaries, reject empty/invalid primitive tokens and negative offsets. In read_object_properties U 6993–7020, verify value end stays within the supplied object, then skip whitespace from the exclusive end and require comma followed by another property or exactly the object close; remove blind `+1` and permissive comma skipping. Apply equivalent state checks to read_json_row_key U 6602–6727, get_result_count U 5918–5944 and build_expected_index U 6418–6521; early key return must not be presented as full object validation. Verify results/count envelope properties structurally rather than locating the first textual occurrence U 6532/5862.

Selftests: valid nested mixed objects/arrays with escaped delimiters; scalar final array elements; missing/leading/repeated/trailing commas; missing value/colon; wrong close type; truncated string/array/object; boundary overrun; duplicate ordinary and key properties; invalid primitive, invalid escape/control, negative offsets; envelope `results`/`__count` lookalikes inside other properties. An actual strict SAP parser can instead validate once if available, with a target-runtime memory check for large fixtures.

### F5 — Python reachability mistakes foreign calls for local helper calls (structural false assurance)

Evidence P 257–260 matches any declared helper token followed by `(`, ignoring `->`/`=>` receiver. An isolated call to the unchanged function with tokens for `foreign->helper( )` returned `['helper']`. A synthetic leaf containing only that foreign call was reported assertion-reachable when the *unused local* helper contained an assertion.

Surgical change: in local_calls P 257–260, retain a candidate only if unqualified, or explicitly qualified by `me->`; exclude other instance/class receivers. Preserve genuine template-expression references. In audit P 415, still detect an explicit `me->leaf( )` category bypass. Do not describe the result as control-flow reachability: unreachable branches also count at P 288–297.

Selftests: bare helper and me->helper reach an assertion; other->helper / foreign_class=>helper with the same name do not; cycles terminate; comment/literal references do not count; template calls count; IF abap_false bodies remain expressly syntax-only, not runtime proof.

### F6 — Python lexer loses valid indented multiplication continuations (scanner defect)

Evidence P 61–72 leaves line_start true while consuming leading whitespace and treats `*` as a comment whenever line_start is true. ABAP star comments require column one; `x = 2` followed by an indented `* 3.` is an arithmetic continuation, not a column-one comment. The lexer drops the continuation and its terminating period.

Surgical change: make column-one detection explicit in tokens P 61–72, resetting it only on newline and clearing it on any preceding character, including indentation; retain quote-comments at any column. Do not simply treat every indented star line as a comment.

Selftests: true column-one star comment ignored; indented multiplication continuation retained with its period; quote comment after indentation ignored; mixed statement boundaries; section banners in current sources still ignored when truly column-one.

### F7 — Legacy commented METHODS chains are misidentified (legacy mapping defect)

Evidence P 959–969 reads tokens from commented declarations but inserts declaration[1] as a single name. For `* METHODS: one FOR TESTING, two FOR TESTING.`, that token is `:`, not `one`, and `two` is never individually recognized.

Surgical change: replace single-name insertion P 968–969 with the same colon/comma chain grouping used by parse P 188–204; individually add only each group's FOR TESTING declarations. Validate owner exists, and end at the declaration's terminating period. Keep implementation lines commented.

Selftests: one commented declaration, chained two declarations, mixed testing/non-testing chain, multiline continuation, deferred/friend stanza, exact class-qualified rename mapping, comment-only legacy body and stale renamed reference.

### F8 — Sorting oracle decodes already-decoded property values (cross-cut caller defect)

Evidence: `read_result_property` U 6805–6811 obtains a raw token and **already calls unquote_json**; `read_first_result_property` delegates to it. `assert_rows_sorted` U 6058–6066 calls read_result_property and then **calls unquote_json again** on its result. A legitimate string value containing surrounding literal quote characters, such as `"Z"` (including those two quote characters as business data), becomes `Z` on the second call. This changes comparison order: `[A, "Z"]` is ascending after the second decoding (`A`, `Z`), although leading literal quote sorts before `A` in the decoded original values. An actually ascending `["Z", A]` can conversely fail. This remains a defect even after fixing F1's escape decoder.

Surgical change: replace U 6064–6066 with `lv_current = lv_token.`; retain the separate documented null/trim handling U 6068–6074 only if that normalization is intended. Do not apply a JSON token decoder to read_result_property/read_first_result_property results elsewhere. Alternatively change their contracts to return genuinely raw tokens and update **every** dependent key/filter/select/sort caller consistently; removing just the redundant sorting call is the smaller safe change.

Selftests: supplier/reviewer values containing literal surrounding quotes, embedded backslashes and literal escape-like text; assert both correct ascending/descending order and rejection of the reversed order. Document that trimming and treating decoded text `NULL` as initial at U 6068 are additional normalization allowances, not exact raw-string ordering. No sorting runtime was executed for this review.

Related caller coverage gap: read_result_property U 6802–6807 silently returns initial text for a missing property. assert_rows_sorted then normalizes initial text to zero for numeric fields or empty string for text fields (U 6078–6124); an entire response with the sorted field omitted can satisfy the ordering assertion. Add an explicit property-presence check in the sorting oracle before comparing values, or change its reader contract to distinguish absence from a present initial value. Test omitted fields separately from legitimate empty/null fields; do not conflate this gap with a production sorting defect.
