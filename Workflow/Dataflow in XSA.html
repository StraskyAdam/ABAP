① User Roles — How the System Identifies Who Is Logged In
On login, UI calls common.getUserRole(emailId) → reads OData entity userRole → backed by HANA Calculation View CV_getUserRoleConfig → reads from Z-table ZT_CONFIG_ROLES.
This table stores the user's role, their assigned company codes, management units and cost centers. The result sets loginUserRole — passed as IP_POOWNER to every backend OData call. This single parameter controls what data each user sees across all 3 dashboard tabs.
ZT_CONFIG_ROLES fields: USER_ROLE · USER_EMAILID · USER_ACCESS · COMPANY_CODE · MANAGEMENT_UNIT · COST_CENTER (NCLOB)
Managed by Admin via insertUserRole.xsjs → procedure insertUserRoleConfig (UPSERT)
PO Owner / PO Preparer
👤 PO Owner Role
ZT_CONFIG_ROLES.USER_ROLE = 'PO_OWNER' → IP_POOWNER = 'X'
Who: Person responsible for a PO (PO_REQUESTOR or PO_PREPARER in EKPO)
What they see: Only POs where their email matches EKPO.PO_REQUESTOR or EKPO.PO_PREPARER

 LOWER(PO_REQUESTOR) LIKE :email OR LOWER(PO_PREPARER) LIKE :email

Who: TBS Finance, Finance, or Admin — USER_ROLE stored in ZT_CONFIG_ROLES

③ Key Editable & Calculated Fields
Services Completed Amount
TOTALWORKCOMPLTODATE
What: Reviewer manually enters how much of the service contract has been completed in monetary value.

Stored in: ZT_EDGE_SERVICEPO_STATUS.TOTALWORKCOMPLTODATE via updateServPOStatus (UPSERT)
Read in: TF_getOpenAllPO → edgePO.totalworkcompltodate → passed as iv_edgeWTDAmt into SF_accrualMethod
UI validation: Cannot exceed PO Value · Cannot be negative · Only for Service POs
💼 Business: The amount of work confirmed completed to date. Used as the WTD (Work To Date) basis for accrual calculation.
% of Services Completed
TOTALWORKCOMPLPERCENT
What: Reviewer manually enters the percentage of service contract completed.

Stored in: ZT_EDGE_SERVICEPO_STATUS.TOTALWORKCOMPLPERCENT via updateServPOStatus
Passed to: SF_accrualMethod as iv_totWrkCompPer
UI validation: Max 100 · Not negative · Max 1 decimal place
💼 Business: Works in tandem with Services Completed Amount — reviewer enters either or both. Used in WTD accrual method.
Goods Received to Date
GRVALUE
What: Read-only field — how much goods/services have been physically received (GR) in SAP.

Source: SAP table EKBE (PO History), filter: bewtp = 'E' (GR movements only)
Calculated in: TF_getPOGRValue → CV_getPO_GRValue calculation view
grvalue = SUM( menge × netpr / peinh )
shkzg = 'S' → debit (positive)  |  shkzg = 'H' → credit/reversal (negative)
JPY / VND: × 100 before calculation
Date cutoff: if today is day 1–6 → last day of previous month, else last day of current month
Used for: AMOUNTACCRUED formula (Material POs)
💼 Business: For Material POs, GR Value replaces WTC as the basis for accrual — the system accrues the difference between what was received and what was already invoiced.
Amount to be Accrued
AMOUNTACCRUED
What: Read-only calculated field — how much needs to be accrued this month.

Calculated in: HANA Calculation Views (CV_getOpenPO, CV_getThresholdPO, CV_getOpenPOReport) as a calculated attribute — not in SF_accrualMethod.
Service PO (pstype='9'):
  AMOUNTACCRUED = MAX(0, TOTWRKCOMPAMT − INVVALUE_CAL)

Material PO (pstype='0'):
  AMOUNTACCRUED = MAX(0, GRVALUE − INVVALUE_CAL)

AMOUNTACCRUED_USD = ROUND(EXCHANGERATE × AMOUNTACCRUED, 2)
INVVALUE_CAL = Invoice Amount already posted to date
💼 Business: The actual journal entry amount Finance needs to post as accrual. It prevents double-counting already invoiced amounts.
Mark as Reviewed
STATUS · MARKASREVIEWED
What: Reviewer confirms they have reviewed this PO for the current month.

What gets saved to ZT_EDGE_SERVICEPO_STATUS:
 STATUS = 'Reviewed' · MARKASREVIEWED = 'X'
 CHANGEDDATE = current date · REVIWED_BY = logged-in email
 TOTALWORKCOMPLTODATE + TOTALWORKCOMPLPERCENT from UI

Monthly reset: There is no physical batch reset job. The STATUS field stays 'Reviewed' in the database. The reset is a read-time calculation inside TF_getOpenAllPO — if changeddate has passed the ACCRUAL_REVIEW_DATE cutoff, the function returns 'Pending' even though the database still holds 'Reviewed'. Exception: po_closure='true' → always 'Reviewed', never resets.
💼 Business: Monthly confirmation that the reviewer has checked and agreed the accrual amount. Expires automatically each month after the review cutoff date.
Straight Line Method / Accrual Method
STRAIGHTLINEMTHD · ACCRUALMETHOD
What: Checkbox allowing reviewer to override the accrual method from WTD to STL or vice versa.

Visible for: Service POs only (Over $50k and Under $50k). Commented out for Material POs — Material has no accrual calculation.

XSA chain when checkbox is changed:
UI checkbox change
→ OData: /methodParameters(IV_POVALUE, IV_POCURRENCY, IV_WRKSTRTDATE,
         IV_WRKENDDATE, IV_ACCRUALMETHOD='STL', IV_TOTWRKCOMPAMT,
         IV_TOTWRKCOMPPER, IV_EDGEWTDAMT, IV_PSTYP, IV_COMPANY)/Results
→ CV_accrualMethod.hdbcalculationview
→ TF_accrualMethod.hdbfunction
→ SF_accrualMethod (called ×5)
→ returns: TOTWRKCOMPAMT, TOTWRKCOMPPER, STRAIGHTLINEMTHD, ACCRUALMETHOD
This is not saved — it only updates the displayed value in real time. Save happens on "Mark as Reviewed".

Under $50k note: Checkbox is visible but backend forces STL regardless.
💼 Business: Reviewers can switch between Straight Line and Work To Date per PO. The system recalculates the accrual amount instantly so the reviewer sees the impact before saving.
Eligible for Closure
PO_CLOSURE · POCLOSURE_FLAG
What: Checkbox to mark a PO as fully completed and ready to close in Ariba.

Flow when checked:
1. UI shows confirmation popup (POClosurePopUp fragment)
2. On confirm → PO_CLOSURE = 'true' added to save payload
3. updateServPOStatus.xsjs saves to ZT_EDGE_SERVICEPO_STATUS.PO_CLOSURE = 'true'
4. Ariba SOAP call: LineItemsPOCloseImportRequest with Closed=4, SAPPOLineNumber=LINEITEM, UniqueName=EKKO.UNSEZ
5. POCLOSURE_FLAG = 1 set in UI model → editable fields (amount, %, STL checkbox) become disabled
6. STATUS = 'Reviewed' permanently — never resets monthly

Effect on accrual: AMOUNTACCRUED = 0, ACCRUALMETHOD = 'WTD', STRAIGHTLINEMTHD = ''
💼 Business: When a contract is fully completed, reviewer marks it for closure. The system automatically notifies Ariba to close the shopping cart lines — no manual Ariba step needed.
New PO Identification
POCREATEDAT (UI-side only)
What: A red ❤ icon with "New PO" label appears below the table when at least one PO was created in the current month.

No backend call — purely UI-side logic in common.js setNewPOIconVisibility():
allDataAct1.filter(e => e.POCREATEDAT.getMonth() + e.POCREATEDAT.getYear() === new Date().getMonth() + new Date().getYear() ).length > 0 → show icon
Runs after OData data is loaded into the UI model. Compares POCREATEDAT (from EKKO.AEDAT) with current month + year.
💼 Business: Visual indicator that alerts reviewers a new PO appeared in their list this month — helping them spot new contracts that need attention.
Monthly Status Reset
STATUS (read-time logic, no DB reset)
What: 'Reviewed' status automatically appears as 'Pending' after the monthly cutoff — but no batch job or procedure resets it.

How it works: The STATUS field in ZT_EDGE_SERVICEPO_STATUS stays 'Reviewed' permanently. The reset is a calculated CASE expression inside TF_getOpenAllPO and TF_getOpenAllThresholdPO evaluated fresh on every data load.

Rules (simplified):
IF po_closure = 'true' → always 'Reviewed'
IF changeddate same month AND day ≥ ACCRUAL_REVIEW_DATE → 'Pending'
IF changeddate previous month AND today > day 6 → 'Pending'
IF changeddate > 1 month ago → always 'Pending'
ELSE → 'Reviewed'
ACCRUAL_REVIEW_DATE = day of month, read from ZT_CONFIG_VALUES.
💼 Business: Reviewers must re-confirm their POs each month. The system enforces this by treating old 'Reviewed' records as 'Pending' at read time — without any overnight batch job.

📊 PO Accruals Dashboard

Loaded on page open for the logged-in user.
Sends 3 separate OData requests — one per tab.
🔵 To Act Upon — Over $50k

Facade / Orchestrator
TF_getOpenPO
1. Reads user decimal format from CV_getUserDetails (X = dot, space = comma, Y = space)
2. Reads last-month "Services Completed Amount" from ZT_EDGE_AUDITLOG → lastMonthwrkcomp column
3. Calls TF_getOpenAllPO
4. Removes exclusion POs (ZT_EDGE_EXCLUSIONPO)
5. STRING_AGG with ';' for multi-line account assignment: GL Account · Cost Center · Internal Order · Profit Center · Asset ID · Management Unit · Distribution %
6. Formats totwrkcompamt_char with locale-correct decimal separator
7. Derives pstype_text (Service / Material) and poclosure_flag (0 / 1)
💼 Business: Final output per row = one PO line item with all columns visible to the reviewer.
Enrichment Function (JOIN Layer)
TF_getOpenAllPO
1. Calls TF_getOpenPOQueryWithEmail('1', pstype) → filtered PO keys
2. LEFT JOINs: EKPO · EKKO · LFA1 · T001 · EKKN · CSKT · CSKS
3. LEFT JOIN ZT_EDGE_SERVICEPO_STATUS — status, accrualMethod, WTD amount
4. LEFT JOIN ZT_EDGE_EXCHANGERATE — exchange rates
5. LEFT JOIN ZT_POLINE_AUDIT → last_notif_on, notif_24_hr
6. Calls SF_accrualMethod ×5 per row → TOTWRKCOMPAMT, USD amount, %, straightlinemthd, accrualMethod
7. Evaluates Reviewed / Pending via read-time CASE (changeddate vs ACCRUAL_REVIEW_DATE)
8. Japan/Brazil rule: pstyp='0' + zstart_date + bukrs IN Japan/Brazil → reclassified as '9'
⚠ SF_accrualMethod is called 5× per row — HANA scalar functions return one value per call.
💼 Business: PO value, service dates, accrual method, amount to accrue and review status combined into one row.
Query + Threshold Filter
TF_getOpenPOQueryWithEmail  (IP_THRESHOLD='1')
Returns only: EBELN · EBELP · POOWNER_EMAIL

Indirect Services (pstyp='9'): pstyp='9' AND erekz IN (' ','') AND bsart='ZARP' AND zstart_date≠'00000000' AND zend_date≠'00000000' UNION Japan/Brazil pstyp='0' with zstart_date set

Indirect Materials (pstyp='0'): pstyp='0' AND bukrs NOT IN Japan/Brazil AND erekz IN (' ','') UNION Japan/Brazil pstyp='0' with zstart_date='00000000'

Threshold (HAVING): SUM(EKPO.netwr) per PO number > SF_ConvertCurrency(threshold_USD → waers). Threshold from ZT_PO_THRESHOLD.

IP_POOWNER='X': adds LOWER(PO_REQUESTOR) LIKE email OR LOWER(PO_PREPARER) LIKE email
IP_POOWNER='': filters via TF_UserConfigCompanyCodes + TF_UserConfigCostCenter + TF_UserConfigManagementUnit
💼 Business: Only POs whose total value across all line items exceeds the threshold (e.g. $50k USD) are returned. Threshold is configurable in ZT_PO_THRESHOLD — not hardcoded.
🟢 To Act Upon — Under $50k
OData EntitySet: thresholdParameters
IP_PSTYPE = '9' → Indirect Services IP_PSTYPE = '0' → Indirect Materials
IP_THRESHOLD = '2' (SUM netwr ≤ threshold)
Smaller POs — Straight Line method always applied for Service
Facade / Orchestrator
TF_getOpenThresholdPO
1. Reads user decimal format from CV_getUserDetails
2. Reads last-month "Services Completed Amount" from ZT_EDGE_AUDITLOG
3. Calls TF_getOpenAllThresholdPO
4. Removes exclusion POs (ZT_EDGE_EXCLUSIONPO)
5. Reads ZT_POLINE_AUDIT directly for notification flags
6. STRING_AGG for all multi-value account assignment fields
7. Same output format as TF_getOpenPO
ℹ Structurally identical to TF_getOpenPO. Only difference: delegates to TF_getOpenAllThresholdPO.
💼 Business: POs below threshold. Accrual is always Straight Line — no manual WTD entry needed.
Enrichment Function (JOIN Layer)
TF_getOpenAllThresholdPO
1. Calls TF_getOpenPOQueryWithEmail('2', pstype) → under-threshold PO keys
2. Identical JOINs as TF_getOpenAllPO
3. Key difference: for Indirect Service POs under threshold, accrualMethod is forced to 'STL' regardless of ZT_EDGE_SERVICEPO_STATUS
4. Same Reviewed/Pending read-time logic and Japan/Brazil override
💼 Business: Under $50k Service POs always use Straight Line — system does not allow WTD for small contracts.
Query + Threshold Filter
TF_getOpenPOQueryWithEmail  (IP_THRESHOLD='2')
Same PO selection logic as Over $50k branch (pstyp rules, erekz, bsart='ZARP', Japan/Brazil UNION, PO Owner vs TBS filter).

Threshold difference: HAVING SUM(EKPO.netwr) ≤ SF_ConvertCurrency(threshold_USD → waers)
Same ZT_PO_THRESHOLD value — applied with ≤ instead of >.
💼 Business: Both branches together cover 100% of open POs. The split point is the same configurable value.
🔴 For Information Only
OData EntitySet: exclusionPOParameters
Source: ZT_EDGE_EXCLUSIONPO (nightly staged)
No IP_PSTYPE / IP_THRESHOLD — shows all excluded POs
Excluded from accrual — shown for transparency only
Facade / Orchestrator
TF_getExclusionPOs
1. Calls TF_getOpenPOQueryWithEmail for all 4 combinations (threshold '1'+'2', pstype '9'+'0') → UNION ALL
2. Reads ZT_EDGE_EXCLUSIONPO (pre-staged)
3. Inverse filter — keeps only POs that ARE IN the exclusion table
4. Calls TF_getPODetail for full data enrichment
5. Aggregates RULETYPE: GL → "Cost Element (GL/BL)" · CC → "Cost Center" · PC → "Profit Centre" · PO → "Purchase Order" · VD → "Vendor" · IV → "Internal Order"
💼 Business: Reviewers see why a PO was excluded. No accrual action needed — purely informational.
Z-Table — Nightly Staged
ZT_EDGE_EXCLUSIONPO
Populated by exclusionStaging.hdbprocedure (nightly or on-demand):

1. Loads ALL open POs (threshold '1'+'2', pstype '9'+'0')
2. Calls TF_checkPOExcl_Mod for rule evaluation
3. DELETE + INSERT (full refresh)

Fields: PONUMBER · ITEMNO · PSTYPE · RULETYPE · LAST_REPLICATED_AT
One PO can match multiple rules — all stored separately, aggregated with ';' in display.
💼 Business: Exclusion rules maintained by Finance/Admin apply automatically each night. New rules take effect the next morning.
Exclusion Check Function
TF_checkPOExcl_Mod
For each PO: JOINs EKPO · EKKO · LFA1 · EKKN → checks each rule type against configured ranges:
bukrs range · sakto range (GL) · kostl range · prctr range · aufnr range · lifnr exact (vendor) · ebeln exact (PO)
Returns: PONUMBER · ITEMNO · RULETYPE per match

Scalar Function — called ×5 per row
SF_accrualMethod
Purpose: Determines accrual amount for a Service PO. Material POs return zero.

Decision logic:
• Method=NULL, no WTD → STL  |  Method=NULL, WTD exists → WTD
• Method='WTD', no amount → fallback STL  |  Method='WTD', amount exists → WTD
• Method='STL' → always STL

5 outputs per call: TOTWRKCOMPAMT_OUT · TOTWRKCOMPAMT_USD_OUT · TOTWRKCOMPPER_OUT · STRAIGHTLINEMTHD · ACCRUALMETHOD_OUT
💼 Business: The "Amount to be Accrued" column driver. Reviewers can switch between STL and WTD — system recalculates instantly via CV_accrualMethod → TF_accrualMethod → SF_accrualMethod.
Scalar Function — called from SF_accrualMethod
SF_calcSTL_wtdAmountPer
Straight Line calculation based on elapsed contract months (not days).

Via SF_getMonthDiff:
• MONTH_BET = total months start → end
• MONTH_BET_CRR = elapsed months start → today
• Day > 15 → round up to next month · Day ≤ 15 → round down
• If contract already ended → treat as 1/1 (full amount)

Formula: stl_amt = ROUND((povalue / MONTH_BET) × MONTH_BET_CRR, 2), capped at povalue
stl_per = ROUND((stl_amt / povalue) × 100, 1)
💼 Business: 12-month contract $120k — after 3 months = $30,000 (25%). Mid-month rounding ensures consistency at month-end close.
Scalar Function
SF_ConvertCurrency
Converts amounts between currencies using ZT_EDGE_EXCHANGERATE (not SAP TCURR).

JPY / VND special handling: values stored ÷100 in EKPO → system multiplies by 100 before conversion.

Used for: PO value → USD · $50k threshold → PO currency · Accrual amounts → USD
💼 Business: All amounts shown in both PO currency and USD so Finance can compare accruals across countries.

Status Calculation — read-time CASE in TF_getOpenAllPO / TF_getOpenAllThresholdPO
Reviewed → Pending Reset Rules (no batch job — calculated on every data load)
po_closure='true' → always Reviewed (permanent, never resets)

status='Reviewed' — when does it stay Reviewed?
• Previous year → Reviewed only on days 1–6 of current month
• Exactly 1 month ago → Reviewed only on days 1–6 of current month
• More than 1 month ago → always Pending
• Same month: changeddate < REVIEW_DAY and today ≥ REVIEW_DAY → Pending (missed cutoff)
• Same month: changeddate ≥ REVIEW_DAY → Reviewed

status='Pending' or NULL → always Pending
💼 Business: Reviewed status expires each month after the ACCRUAL_REVIEW_DATE cutoff. No overnight job — the logic runs fresh on every page load.

Scheduled — Nightly Procedure
